## 2. Phase 0 구현 계획

### 2-1. 전제: 수치 원장 규약

결함 8종 중 1(표 행 이름 오독), 2(분모 단정), 3(기준연도 불일치), 7(표 미반영)은 자유 산문에서는 기계로 못 잡는다. 어느 숫자가 어느 표의 어느 행에서 왔는지가 문서 안에 없기 때문이다. 그래서 Phase 0의 첫 산출물은 검사기가 아니라 **문서 규약**이다.

- 제안서 1건은 `draft.md`(본문)와 `ledger.md`(수치 원장)로 구성한다. 기본사회위 건의 `참고자료_260923.md`(조문 원문, 출처 검증표, 확인하지 않은 것 목록)가 이미 이 역할을 하고 있으므로 그 구조를 표준으로 굳힌다.
- 원장의 수치 한 건은 표 한 행이다: `id | 값 | 단위 | 기준기간 | 모집단(분모) | 출처 URL | 원문 표의 행 이름 | 접근일`.
- 본문에서 수치를 쓸 때는 바로 뒤에 `[#id]`를 붙인다. 본문에서 두 수치를 나누거나 빼서 만든 값은 `[#c1 = #a / #b]`처럼 산식을 적는다.
- 미확인 목록의 항목도 `[?id]`를 가지며, 본문에서 그 사실을 언급하는 문장은 같은 마커를 달아야 한다.

이 규약을 지키지 않은 문서는 검사기가 "규약 위반"으로 먼저 거른다. ⑤작성 단계의 완료 정의("모든 수치에 출처와 기준일이 붙어 있다")가 곧 이 규약이다.

### 2-2. 결함 8종의 기계 판정

| # | 결함 | 판정 방법 | 확실성 |
|---|---|---|---|
| 1 | 표의 행 이름 오독 | 본문에서 `[#id]` 앞 문장의 라벨(명사구)과 원장의 "원문 표 행 이름"을 대조한다. 원장 행 이름의 핵심 명사가 본문 문장에 없거나 다른 원장 항목의 행 이름과 일치하면 플래그. 기본사회위 건이라면 "거주지 시군구 내"라고 쓴 문장 옆의 원장 행 이름이 "현재 살고 있는 읍·면·동"이므로 잡힌다 | 규약 준수 문서에서 기계. 산문 표현이 행 이름과 멀면 오탐이 나므로 LLM 판정 A가 2차 |
| 2 | 분모 단정 | 산식 앵커 `[#c = #a / #b]`에서 `a`와 `b`의 모집단 필드가 다르면 플래그. 산식 없이 "X 중 Y%" 꼴로 쓴 비율은 원장에 분모 필드가 비어 있으면 플래그 | 기계 |
| 3 | 기준연도 불일치 | 산식 앵커의 피연산자 기준기간이 다르면 플래그. 한 문장이나 표 한 행에 두 수치가 있고 "대비, 증가, 감소, 배" 같은 비교 표지가 있으면서 기준기간이 다르면 경고 | 기계 |
| 4 | 출처 없는 숫자 | 단위가 붙은 숫자(%, 원, 건, 명, 개소, p) 뒤 20자 안에 `[#id]`나 각주가 없으면 플래그. 예외: 조문 번호, 날짜, 목차 번호, 배점표 인용 | 기계 |
| 5 | 조문 항·호·목 혼동 | `제N조제M항제K호` 패턴을 파싱해 원장의 조문 원문 블록에서 해당 위치 텍스트를 찾고, 본문 따옴표 안 인용문이 그 텍스트의 부분 문자열인지 본다. 원문 블록이 없으면 "미대조" 목록으로 출력한다 | 원문이 원장에 있을 때 기계. 없으면 E6과 같은 성격의 escalation |
| 6 | 본문 단정 vs 미확인 목록 충돌 | 미확인 목록의 각 항목에서 명사와 숫자를 뽑아 본문 문장을 검색한다. 매치된 문장의 종결이 단정형(이다, 했다, 된다, 이며)이고 완화 표지("확인되지 않", "추정", "으로 보인다", "가능성", "미확인")와 `[?id]` 마커가 모두 없으면 플래그 | 기계로 잡히지만 키워드 매칭이라 오탐과 누락이 있다. 대안으로 `[?id]` 마커 규약을 강제하면 "마커 없는 단정 문장"만 보면 되므로 결정적이 된다. LLM 판정 B에도 이 대조를 명시 항목으로 넣는다 |
| 7 | 개정 후 본문만 고치고 표 미반영 | 두 겹으로 잡는다. (a) 문서 내부: 같은 `[#id]`가 본문과 표에서 다른 값을 달고 있으면 플래그. (b) 개정 diff: 개정 전후 diff에서 바뀐 숫자 쌍(old→new)을 뽑고, old 값이 개정본 어디에든 남아 있으면 위치와 함께 플래그. (b)는 규약 없이도 결정적으로 잡힌다 | 기계 |
| 8 | 상호참조 깨짐 | 헤딩에서 절 번호를 수집하고 본문의 `N-M절`, `제N장`, `표 N`, `부록 X` 참조가 실재하는지 본다 | 기계 |

**반영 검증(지시서 5-4)** 은 7(b)와 같은 엔진이다. 레드팀 리포트의 지적 항목마다 `위치 앵커`와 `기대 변화(old→new 또는 삭제)`를 적어 두면, 개정본에서 old가 남아 있는지와 new가 있는지를 기계로 대조한다. 부분 반영은 "old 잔존 위치 목록"으로 나온다. 이번 핀테크 건에서 24건 중 5건이 부분·미반영이었다는 것이 정확히 이 검사의 대상이다.

어려운 것을 솔직히 적으면 1번과 6번이다. 둘 다 규약 없이는 LLM 판정으로만 잡히고, 규약이 있어도 산문 표현이 다양하면 오탐이 난다. 그래서 Phase 0 완료 판정은 "규약을 지킨 문서에서 8종 전건 검출"로 읽는다. 규약 미준수 문서에 대해 전건 검출을 약속하면 거짓말이다.

### 2-3. 하네스 구조

```
evals/
  contract.md              수치 원장 규약 (2-1)
  golden/GC-01/            input.md (62점 버전), ledger.md, expected.json, clean.md (승인본)
  golden/GC-02/            48점 버전
  golden/GC-03/            초안 4건
  inject/                  결함 8종 주입 스크립트. clean.md에서 변형본 8개 생성, 정답은 스크립트가 기록
  checks/                  기계 판정기. 결함별 1파일, 표준 라이브러리만
  run.py                   골든 3건 + 주입 24건 실행 → 검출/누락/오탐 표
  baseline.json            GC-01 1회차 검출 수. 회귀 기준선
```

- `expected.json`은 결함 1건이 `{id, 심각도, 위치 앵커, 결함 유형(8종 중), 정답 문장}` 이다. 골든케이스의 정답은 사람이 확정한 것이므로 Notion 페이지의 "적대적 검증에서 고친 것" 목록을 그대로 옮기고, 8종 분류만 내가 붙인다.
- `korean-prose`의 `check.py`는 SKILL.md 본문에 코드로만 있어서 파일로 꺼내 `checks/prose.py`로 둔다. 재구현이 아니라 복사다. 단 이 검사기는 가운데점(·)을 금지 항목으로 잡는데 기관명("금융위원회 · 한국핀테크지원센터")과 조문 인용에서 오탐이 나므로 결과를 경고로만 다룬다.
- 판정 순서: 규약 위반 → 결함 8종 → 분량·서식·파일명 → 문체. 앞 단계가 실패하면 뒤를 돌리지 않는다.
- Phase 0 완료 판정: `clean.md` 3건에서 오탐 0, 주입본 24건 전건 검출, GC-01 기준선 기록.

## 3. 지시서에서 모순되거나 실현 불가능한 지점

1. **참조 자산이 이 환경에 없다.** 0번 표의 「공모전 파이프라인 설계 v1」과 골든케이스 3건은 claude.ai Project 안에 있고 Claude Code는 거기에 닿지 않는다. 지시서 8번의 "Phase 0 반나절"은 이 파일들이 저장소에 있다는 전제다. 파일을 `evals/golden/`에 넣어 주거나, 한 번 붙여넣어 주면 내가 저장한다.

2. **`career-report`의 `qa.py`는 존재하지 않는다.** 동기화된 스킬에는 `career-report/`에 SKILL.md와 references만 있고, `qa.py`는 `zb-lecture-pipeline/scripts/qa.py`(PPTX 검사기)뿐이다. 지시서 5-2가 말한 양방향 검증 방식은 이쪽을 가리키는 것으로 가정하고 진행한다.

3. **"결함본 8종 전건 검출"은 규약 없이는 불가능하다.** 2-1과 2-2에 적었다. 완료 판정의 문장을 "수치 원장 규약을 지킨 문서에서"로 좁혀야 한다. 규약 자체가 ⑤작성의 완료 정의를 구체화한 것이므로 지시서와 충돌하지는 않는다.

4. **S3의 80%와 Phase 0의 100%가 다른 것을 잰다.** Phase 0 완료 판정(주입본 전건 검출)은 기계 판정기 기준이고, S3(심어둔 오류 검출률 80%)는 골든케이스의 사람 확정 정답 기준이다. 둘을 합치면 앞뒤가 안 맞으니 S3는 "골든케이스 정답 목록 대비 LLM 판정 포함 검출률"로 읽는다.

5. **E7이 거의 매 건 발생한다.** 문서 포맷 리서치에서 정책 공모전 16건 중 9건이 HWP/HWPX 서식이었다. 지금 정의로는 E7이 escalation 예산(주 3회)을 혼자 다 쓴다. HWPX는 python-hwpx로 양식 채우기가 되는 것을 샌드박스에서 확인했으므로, E7을 "바이너리 HWP 전용 요구" 또는 "HWPX 양식 채우기 실패"로 좁히는 것을 제안한다. 웹폼 로그인 쪽도 접수 방식 리서치상 이메일 접수가 가장 흔해서(18건 중 8건) 그대로 둬도 된다.

6. **저장소가 공개(public)다.** 골든케이스는 본인 제안서 원문이고 이력·연락처가 들어 있을 수 있다. 금칙어 목록은 클라이언트명 그 자체라 G1-B다. 둘 다 공개 저장소에 올리면 안 된다. 저장소를 private으로 바꾸거나, 골든케이스와 금칙어를 `.gitignore`로 빼고 로컬 또는 Routines의 API credentials로 주입해야 한다. 이 결정은 Phase 0 착수 전에 필요하다.

7. **Routines의 전제가 지시서에 없다.** 주 1회 무인 실행을 Routines로 하려면 (a) 환경 네트워크 정책을 Custom 이상으로 열고, (b) 코드가 master에 병합돼 있어야 한다. 지금 세션의 정책으로는 정부 사이트가 전부 403이라 ①탐색이 한 건도 못 돈다.

8. **⑧학습의 상관 확인은 표본이 안 나온다.** 연 12~20건에 S7 "3건 이상 쌓인 뒤 상관 확인"은 통계로는 의미가 없다. 지시서가 "초기에는 관측만"이라 했으니 모순은 아니지만, S7을 상관계수가 아니라 "자체채점과 실제 등급의 방향 일치 여부"로 두는 편이 정직하다.

9. **④착안 브리프의 내용이 두 문서에서 다르다.** 지시서 6-2는 브리프에 "정찰 요약, 배점 만점 조건, 이미 죽은 후보와 사유, 착안 질문 5개"를 넣고, Notion 파이프라인 8단계는 Seed에서 "후보 6~8개 도출 후 스코어링"을 시스템이 한다. 지시서를 우선해 브리프는 후보를 새로 만들지 않고 질문만 낸다. 다르게 원하면 알려 달라.

10. **wayfinder 맵과의 관계.** 이 지시서가 맵의 결정 티켓 3개(승인 게이트, 저장소, 피드백 루프)를 사실상 결정했다. 그 티켓은 지시서를 근거로 닫고 맵의 Decisions so far에 적는다. 남는 것은 범위(Q3), 실행 방식(Q2), 프로토타입(Phase 1의 GC-01 실행이 곧 그것)이다.

## 4. 내가 정하고 진행하는 것

- 언어와 도구: Python 3 표준 라이브러리만. 프레임워크 없음.
- 저장소 구조: `evals/`(하네스), `contests/<id>/`(건별), `clusters/<발주처>/`(재사용 자산), `docs/`. 상태는 Notion만 갖는다.
- 문서 규약(2-1)을 ⑤작성의 완료 정의로 채택한다.
- LLM 판정 A, B, C는 Phase 1에서 만들고 Phase 0에서는 인터페이스(입력 파일, 출력 JSON 스키마)만 고정한다.

Q1~Q3의 답과 3-6(공개 저장소)의 결정을 받으면 Phase 0을 시작한다. 골든케이스 파일 3건이 오기 전까지는 규약 문서, 주입 스크립트, 판정기 8종까지 만들 수 있고, 골든 3건은 파일이 오면 붙인다.
