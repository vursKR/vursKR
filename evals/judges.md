# LLM 판정과 레드팀 리포트 인터페이스

착수 보고서 §4가 "Phase 0에서는 인터페이스(입력 파일, 출력 JSON 스키마)만 고정한다"고 한 그 인터페이스다. 판정 프롬프트 자체는 Phase 1에서 만든다.

기계 판정기(`checks.py`)가 잡는 것은 `contract.md`의 규약을 지킨 문서에서 결정적으로 판정 가능한 것뿐이다. 산문 표현이 원장과 멀어지는 D1과 D6, 그리고 배점 대비 감점 사유는 기계로 안 잡힌다. 그 몫이 LLM 판정이다.

## 판정자 3인

지시서 5-3의 "서로 통신하지 않는 병렬 LLM 판정 3인"을 이렇게 나눈다. 셋은 같은 입력을 받고 서로의 출력을 보지 않는다.

| 판정 | 맡는 것 | 대응 결함 |
|---|---|---|
| A | 본문 문장의 라벨과 원장 "원문 표 행 이름"의 의미 대조 | D1 2차. 기계 판정이 놓친 의미 어긋남 |
| B | 미확인 목록 대 본문 단정문의 충돌 | D6 2차. `[?id]` 마커 누락분 |
| C | 심사 배점표 대비 감점·탈락 사유 | 8종 밖. `contest-redteam` 스킬이 하던 일 |

C의 범위는 지시서가 판정자별 역할을 나누지 않았으므로 내가 정한 것이다. 다르게 원하면 이 표만 고치면 된다.

## 입력

셋 다 같은 파일 묶음을 받는다.

| 파일 | 내용 | 없을 때 |
|---|---|---|
| `draft.md` | 응모작 본문 | 판정 불가 |
| `ledger.md` | 수치 원장 | 판정 불가 |
| `notice.md` | 공고 원문(배점표 포함) | C만 건너뛴다 |
| 기계 판정 결과 | `run.py check`의 출력 | 빈 목록으로 본다 |

## 출력

판정 1인이 JSON 1개를 낸다.

```json
{
  "judge": "A",
  "findings": [
    {
      "id": "A-1",
      "code": "D1",
      "severity": "치명",
      "line": 9,
      "anchor": "수도권 근무자 중 시군구 밖 통근 비율은 43.1%",
      "claim": "원장 #a2의 원문 행 이름은 '거주지 시군구 내 통근'이라 본문의 '시군구 밖'과 반대다",
      "fix": {"old": "시군구 밖 통근 비율은 43.1%", "new": "시군구 내 통근 비율은 43.1%"}
    }
  ]
}
```

| 필드 | 규칙 |
|---|---|
| `judge` | `A` / `B` / `C` |
| `id` | 판정 안에서 유일. `<judge>-<번호>` |
| `code` | 결함 8종은 `D1`~`D8`, 규약 위반은 `C0`, 배점 관련은 `S` |
| `severity` | `치명` / `중대` / `경미`. 치명은 그대로 두면 실격, 중대는 감점, 경미는 그 외 |
| `line` | `draft.md`의 행 번호. 특정 못 하면 `0` |
| `anchor` | 그 행에 실제로 있는 문자열. 기계가 위치를 다시 찾는 데 쓰므로 지어내면 안 된다 |
| `claim` | 무엇이 왜 틀렸는지 한 문장. 근거는 원장 id나 공고 문장을 인용한다 |
| `fix.old` | 고쳐야 할 현재 표현. 삭제 지적이면 이것만 채운다 |
| `fix.new` | 고친 뒤 표현. 삭제 지적이면 `""` |

지어낸 근거를 막는 규칙 하나: `claim`이 수치를 말할 때는 원장의 `#id`를 인용하고, 공고를 말할 때는 `notice.md`의 문장을 그대로 옮긴다. 둘 다 못 하면 그 항목은 내지 않는다.

## 레드팀 리포트

기계 판정 결과와 판정 3인의 출력을 합친 것이 `contests/<id>/redteam.md`의 부록으로 붙는 `redteam.json`이다. 형식은 위 `findings`와 같고 `judge`가 `machine`인 항목이 섞인다. 중복은 `line`과 `code`가 같으면 하나로 본다.

이 파일이 곧 반영 검증의 입력이다. `fix.old`와 `fix.new`만 있으면 되므로 따로 만들지 않는다.

```
python3 evals/run.py verify contests/<id>/redteam.json contests/<id>/draft.md
```

개정본에 `old`가 남아 있으면 미반영, `new`가 없으면 미반영으로 보고한다. 부분 반영은 잔존 위치 목록으로 나온다.

## 골든케이스 정답 파일

`evals/golden/GC-*/expected.json`은 사람이 확정한 정답이라 형식이 더 얇다. `run.py`가 실제로 읽는 필드는 둘뿐이다.

```json
[
  {"code": "D2", "anchor": "구민 대비 수혜자 비율은 7.3%"}
]
```

| 필드 | 규칙 |
|---|---|
| `code` | 위와 같음. 필수 |
| `anchor` | `input.md`의 해당 행에 실제로 있는 문자열. 필수 |
| `severity`, `claim` | 있으면 기록용으로 남기고 채점에는 안 쓴다 |

케이스 1건은 `input.md`(결함이 있는 판), `ledger.md`, `expected.json`으로 이루어진다. 승인본이 따로 있으면 `clean.md`로 같이 둔다. `evals/golden/`은 `.gitignore` 대상이라 저장소가 private으로 바뀌기 전까지는 커밋되지 않는다.
